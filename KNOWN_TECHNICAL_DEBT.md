Part of the [AI Engineering Handbook](CLAUDE.md). This document tracks known architectural, operational, and documentation debt in the current implementation — conditions that are true today and carry forward-looking risk or friction if left unaddressed.

This document tracks known technical debt. It is not intended to serve as a feature roadmap or enhancement backlog — it does not track feature requests or planned enhancements, which are decided directly with the project maintainers as they arise. An item belongs here only if it describes something about the *current* implementation, not something proposed for the future.

This is the single authoritative source for the detail and current status of every item referenced elsewhere in the handbook as a "known quirk," "known gap," or similar. Other documents may summarize an item briefly; this document owns the detail.

| Notification Center's live-refresh WebSocket ping can fire before its own triggering transaction commits | `api/services/admin_audit.py` (`record_admin_audit_event` broadcasts via `_broadcast_audit_event_ping` before the caller's later `db.commit()`) → `FEATURE_INVENTORY.md` § 9 | Accepted | `record_admin_audit_event` only stages the audit row (`db.add`); every one of its ~17 call sites commits afterward, on its own schedule. Broadcasting a `{"type":"audit_event"}` ping synchronously inside `record_admin_audit_event` (so it fires from a single, already-existing choke point rather than requiring an insertion at all 17 call sites) means a client that refetches immediately on the ping can occasionally race ahead of the commit and miss the very newest event by one cycle. Self-healing: the next ping, the existing interval poll (`sfa.notificationCenterRefreshIntervalMs`, see Slice 2), or a manual Refresh always catches it — confirmed empirically during verification (a live-browser test that fired two rapid-fire triggers observed one arrive a cycle late, with the other, and both eventually present, before the next real-world trigger). Same accepted-imprecision class as the pre-existing `participant_update` broadcasts in `api/routers/admin_participants.py`, which also aren't guaranteed atomic with their commit. Moving the broadcast to strictly after-commit would require `record_admin_audit_event` to own the commit itself — a change to all 17 call sites' transaction boundaries, out of scope for an additive slice. |
| `NotificationReadState` rows can outlive the notification they describe | `api/models/notification_read_state.py` (`notification_key` is an opaque string, not a foreign key into any of the four source tables) → `FEATURE_INVENTORY.md` § 9 | Accepted | By design (see the Slice 4 design review): `notification_key` reuses each notification's own client-computed `item.id` (e.g. `audit:<uuid>`, `telemetry:<event_id>`) with no FK back to `AdminAuditEvent`/`TelemetryRecord`/`CommunicationMessage`/`CommunicationDelivery` — there's no single table it could point at anyway, since sources span four different models. Telemetry rows are purged by `TelemetryStore.apply_retention()` and messages can be hard-deleted (`delete_message`), so a read-state row can end up referencing a notification that no longer exists. Harmless — an orphaned row is just inert, nothing dereferences it — but no cleanup job exists. If per-user row count ever becomes a real concern, a lazy TTL-based prune (e.g. drop rows older than N days) would be the natural fix; not needed at current scale. |
| Public waiver-signing page has no waiver text to show, and no block on signing, if no `WaiverTemplate` is currently `active` | `api/routers/waivers.py` (`get_public_waiver_signing_page`), `admin-app/public/waiver-signing.html` → `FEATURE_INVENTORY.md` § 7 | Accepted | As of the 2026-07-17 waiver-display fix, the public signing page renders the active `WaiverTemplate.content` before the acknowledgement checkbox, resolved via `waiver_template_lifecycle.get_active_template()` — the same active-template lookup `complete_public_signing()` already used at sign-time, so displayed text and recorded provenance always agree.
